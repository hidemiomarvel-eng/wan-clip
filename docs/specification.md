# WanClip 仕様書

## 1. サービス概要

WanClip は、犬と一緒に利用できるお店や施設の情報を、ユーザー同士で登録・共有できる Web サービスです。

単なる個人用メモではなく、複数ユーザーがスポット情報を投稿し、実際に行ったときの口コミや補足情報を蓄積しながら、犬連れ向けの実用的な情報を共有することを目的としています。

対象は、以下のような犬と一緒に利用できる場所です。

- カフェ
- レストラン
- 宿泊施設
- 観光スポット
- ドッグラン
- その他

## 2. サービスの目的

主な目的は、犬連れユーザーが以下を素早く判断できるようにすることです。

- 犬と一緒に入れる場所か
- どのような条件で利用できるか
- 施設の特性や使いやすさ
- 実際に利用した人の情報やメモ

また、ユーザーが個々の情報を持ち散らばらせず、共有可能な情報源として使えるようにすることを目指します。

## 3. V1 の機能

V1 では、最初の基本機能を実装し、モックデータを使って画面と基本操作を確認できるようにします。

- スポット一覧
- スポット詳細
- スポット新規登録
- スポット編集
- スポット削除
- キーワード検索
- 条件による絞り込み
- 行きたい登録・解除
- 行きたい一覧

V1 では、ユーザー認証や複数ユーザー管理、画像投稿、口コミの厳密な仕組みは実装しません。

## 6. 各画面の役割

### ホーム画面

- サービスの導入目的を伝える
- スポット一覧への入口となる
- 検索やカテゴリの導線を提供する

### スポット一覧画面

- すべてのスポットを一覧表示する
- キーワード検索と条件絞り込みを利用できる
- 一覧から詳細へ遷移できる

### スポット詳細画面

- 施設名や住所、利用条件などの情報を表示する
- 多くの項目は簡潔に見せる
- 編集・削除アクションへ遷移する
- 「行きたい」の登録・解除を行う

### 行きたい一覧画面

- 「行きたい」に登録したスポットだけを一覧表示する
- スポット一覧と同じカード UI を利用する
- カード上のハート操作で「行きたい」を解除できる
- 行きたい一覧から詳細へ遷移した場合、「一覧へ戻る」で行きたい一覧へ戻る

### スポット登録画面

- 施設の基本情報を入力する
- すべての項目を必須にせず、未入力可の設計を想定する
- 登録後、一覧画面または詳細画面へ遷移する

### スポット編集画面

- 既存のスポット情報を更新する
- 元の値を編集しやすくする
- 変更後に詳細画面または一覧画面へ戻る

- 都道府県
- 住所
- 犬が利用できる場所
  - 店内OK
  - テラスのみ
  - その他
- 対応している犬のサイズ
  - 小型犬
  - 中型犬
  - 大型犬
- ドッグランの有無
- 犬用メニューの有無
- 駐車場の有無
- Web サイト URL
- メモ

### データの扱いについて

- すべてを必須にしない
- 未確認項目は空欄または未入力許容
- 将来的には口コミや最終確認日などの補足情報を追記可能にする

### 実装時のトラブル記録: localStorage 登録データの詳細・編集画面表示不具合と React lint 回避

今回の V1 実装では、「新規登録したスポットを一覧から詳細画面・編集画面へ遷移して表示する」機能を追加した際に、保存済みスポットの URL で `スポットが見つかりませんでした` が表示される事象が発生した。

原因は、詳細ページと編集ページの取得ロジックが、ブラウザの `localStorage` を正しく参照できていなかったことにある。詳細ページはモックデータのみを検索し、編集ページはサーバーコンポーネントから `getStoredSpotById` を呼び出していたため、ブラウザにしか存在しない保存データを取得できなかった。

実際には、一覧画面ではモックデータと `localStorage` のデータを合成して表示していたが、詳細・編集ページでは保存データを含まない取得処理になっていたため、保存済みの ID を持つデータが見つからず表示が失敗していた。

修正として、詳細ページでは以下の順でデータを取得するようにした。

- 既存モックデータの中から `id` に一致するスポットを探す
- 一致しなければ `getStoredSpotById(id)` で `localStorage` の保存データを探す
- どちらにも存在しない場合のみ `notFound()` または未発見表示を返す
- 編集ページは client component として実装し、`useParams` で取得した ID を使って `localStorage` の保存データを読み込む

この修正により、一覧で表示している新規登録スポットでも、詳細画面と編集画面に正しく遷移して内容を確認・更新できるようになった。

その後、React の lint ルール `react-hooks/set-state-in-effect` により、`useEffect` 内で `setState` を直接呼んでいた実装が再度問題になった。特に、一覧画面や詳細画面で `localStorage` から値を読み込んだあとに `setState` する書き方を行っていた場合、効果的な同期ではなく「レンダリングのたびに再描画が誘発される」実装になるため、eslint がエラーとして検出した。

今回の回避策として、次のように修正した。

- `useEffect` で `setState` を行うのではなく、`useState(() => getStoredSpots())` のような lazy initializer を使って初期値を直接作る
- `useMemo` の中で `typeof window === "undefined"` を確認し、サーバー側ではモックデータのみを使い、クライアント側では `localStorage` を安全に参照する
- 画面遷移や保存データ参照のロジックは、一覧・詳細・編集・削除で同一の取得方針に揃える

これにより、データ取得の正しさと React の推奨パターンの両方を満たす状態にした。

今後も、モックデータと `localStorage` を併用する機能を追加する場合は、データ取得元の分岐を明示し、一覧・詳細・編集・削除で同じ識別ロジックを使うようにすることが重要である。

## 12. 将来の認証・DB化と共同編集方針

### ユーザーとスポットの関係

スポットを登録したユーザーは、そのスポットの所有者とは扱わない。

登録されたスポットは WanClip 全体で共有する情報とし、将来的にはログインユーザー同士で情報を更新・最新化できる仕組みを導入する。スポットには、以下の情報を記録する予定である。

- `created_by`: 最初にスポットを登録したユーザー
- `created_at`: スポットの登録日時
- `updated_by`: 最後にスポット情報を更新したユーザー
- `updated_at`: スポット情報の最終更新日時

`created_by` はスポットの所有者を表すものではなく、最初に情報を登録したユーザーを記録するための項目とする。

### スポットの編集・削除

将来的には、ログインユーザーであれば、他のユーザーが登録したスポットについても編集できるようにする。これは、犬連れで利用できる施設の情報をユーザー同士で更新し、最新化するためである。

削除は編集とは分けて扱い、誰でも自由に削除できる仕様にはしない。誤削除や悪意のある削除によって、レビューや「行きたい」などの関連情報が失われることを防ぐためである。

閉店・休業などの状態は、将来的にスポットを物理削除するのではなく、営業状況として管理することも検討する。

### 情報の更新日時

将来的にスポット詳細画面で `updated_at` を利用し、情報の最終更新日を表示する。

表示例:

```text
最終更新：2026年9月24日
```

ユーザーが掲載情報の新しさを判断する材料として利用できるようにする。

### スポット情報に関する注意書き

将来的にスポット詳細画面の下部へ、掲載情報が現在の状況と異なる可能性を伝える注意書きを表示する。

文言は以下を基本とし、既存画面のトーンに合わせて調整する。

> 掲載情報はユーザーから投稿・更新された情報を含むため、現在の状況と異なる場合があります。ご利用前に、施設の公式サイトや公式SNSなどで最新情報をご確認ください。

### セキュリティ・悪用対策

ユーザーがスポット情報を編集できるようにする際は、悪意のある変更や危険な入力を考慮する。

- Web サイト URL は原則として `http://` または `https://` のみを許可する
- `javascript:` などの危険なスキームは許可しない
- 施設名、住所、メモ、レビューなどの自由入力値は、ユーザー入力の HTML をそのまま HTML として描画しない
- 入力値の検証と出力時のエスケープを行い、将来の DB/API 側でも同等の検証を行う

## 13. 認証・Supabase・DB化の方針

今後、Supabase を利用した認証・DB化を検討する。現時点で `localStorage` に保存しているユーザー固有の「行きたい」情報は、将来的にユーザーとスポットの関係として DB で管理する。

「行きたい」は `Spot` 型に状態を直接持たせず、次の組み合わせで管理する。

- `user_id`
- `spot_id`

これにより、スポット自体の共有情報と、ユーザーごとの行きたい状態を分離する。現在の localStorage でも、スポット情報そのものではなくスポット ID を保存する方針を維持する。

レビューについても、以下の関係を DB で管理する予定である。

- レビュー投稿者
- 対象スポット

レビューの編集・削除は、原則として投稿者本人のみが行えるようにする。

認証・DB導入時には、画面上で操作ボタンを制限するだけでは不十分とする。DB側でもユーザーごとの操作権限を制御し、編集・削除・レビュー操作などの認可を実施する。

## 14. 将来検討する機能

### 訪問記録

将来的に、ログインユーザーがスポットへの訪問を記録できる機能を追加する予定である。

訪問記録は単純な「行ったことがある / ない」という boolean ではなく、実際に訪問した 1 回ごとの記録として管理する。同じスポットに複数回訪問した場合も、それぞれ別の訪問記録として残せるようにする。

DB では、以下のような `visits` データを想定する。詳細なカラム構成は DB 実装時に改めて検討する。

- `id`
- `user_id`
- `spot_id`
- `visited_at`
- `created_at`

#### 訪問記録の目的

訪問記録は、単なる「行ったことがあるスポット」の管理ではなく、以下につなげるための機能として位置付ける。

- ユーザー自身のお出かけ履歴
- 掲載されているスポット情報が現在も正しいかの確認
- 変更されていたスポット情報の更新
- レビュー投稿への導線

#### スポット情報の確認

訪問を記録したことだけを理由に、スポット情報の最終確認日を自動更新しない。「訪問したこと」と「掲載情報が現在も正しいことを確認したこと」は別の状態として扱う。

訪問記録後などに、ユーザーへ次のような確認を行うことを検討する。

> 掲載されている情報は現在も合っていましたか？

選択肢のイメージ:

- 情報は合っていた
- 変更点があった
- あとで確認する

ユーザーが「情報は合っていた」と明示的に確認した場合に限り、スポット情報の最終確認日を更新する想定である。「変更点があった」場合は、スポット情報の編集へ誘導することを検討する。

#### 最終確認情報との関係

既に検討している `last_confirmed_at` は、単にスポットが編集された日時ではなく、掲載情報が現在も正しいことを確認した日時として扱う。

将来的には、以下の情報を履歴として残すことも検討する。

- 誰が確認したのか
- どの訪問をもとに確認したのか
- いつ確認したのか

`spots.last_confirmed_at` のみを持つか、確認履歴を別データとして管理するかは、DB 設計時に改めて検討する。

#### レビューとの連携

訪問記録後にレビュー投稿へ誘導する流れを検討する。

```text
訪問を記録
↓
掲載情報が現在も正しいか確認
↓
必要であればスポット情報を更新
↓
レビューを書く
```

ただし、訪問記録をしたことを理由に、レビュー投稿を必須にはしない。

#### マイページでの表示

将来的にはマイページなどから、ユーザー自身の訪問記録を確認できるようにすることを検討する。

表示例:

```text
訪問記録
- 2026/09/24 Wan Cafe
- 2026/09/10 Dog Garden
- 2026/08/15 わんこホテル
```

同じスポットへの複数回の訪問も、それぞれ別の訪問として表示できるようにする。

#### UI 上の表現

「行った」という単純な状態ではなく、「訪問を記録」など、1 回の訪問を記録する機能であることが分かる表現を使用する方針とする。

アイコンは現時点では次の使い分けを想定する。

- ハート: 行きたい
- 足あと: 訪問記録
- 星: レビュー評価

最終的な文言、アイコン、UI は実装時に改めて検討する。

### 情報の最終確認

スポット情報の `updated_at` とは別に、掲載されている情報が現在も正しいことを確認した日時を管理することを検討する。

表示例:

```text
最終更新：2026年9月1日
最終確認：2026年11月20日
```

情報に変更がなくても、実際に利用したユーザーなどが「現在もこの情報で合っている」と確認できる仕組みを想定する。将来的には `last_confirmed_at` などの項目で管理する。

### その他

- 閉店・休業などの営業状況
- 編集内容の差し戻し
- 管理者による情報管理
